2. 双模式架构

模式 A：文档跟随项目（默认）

docs/ 在项目根目录下，与代码一起管理。

项目根/
├── CLAUDE.md
├── docs/
│   ├── CLAUDE.md
│   ├── context/
│   └── ...

适用场景：单仓库项目，文档与代码同生命周期。

模式 B：独立文档仓库

docs/ 在独立 git 仓库中，通过 DOCS_ROOT 环境变量关联。

项目根/              文档仓库根/
├── CLAUDE.md         ├── .git/
├── 代码...           ├── docs/
                      └── ...

适用场景：文档需独立版本管理、跨项目共享文档库。

模式检测优先级

Step 0.1 检查环境变量 DOCS_ROOT ├─ 已设置 → 模式 B（文档根 = $DOCS_ROOT） └─ 未设置 → Step 0.2 Step 0.2 检测 docs/ 是否独立 git 仓库 test -d docs/.git ├─ INDEPENDENT_REPO → 模式 B └─ INLINE → 模式 A

3. AGE（Attractor-Guided Engineering）增强框架

AGE 是 v2.0.0 的核心升级，将三个工程纪律机制内建到文档管线中：

Task Routing 任务路由

根据任务复杂度和风险级别，自动决定 AI 的执行策略。不再"一股脑执行"，而是先分类、再路由。

路由类型触发条件行为
直接执行低风险、单文件、明确 owner doc不问，直接干
计划优先跨模块、中等复杂度先出计划，等确认
先问高风险区域、受保护资源执行前必须确认
阻止最高风险（支付、删除、权限）必须人工介入
仅研究探索阶段只研究报告，不执行
Planning Triggers 计划触发器

当满足以下任一条件时，强制要求先写执行计划再开工：

  • 涉及数据库 schema 变更
  • 跨 3 个以上模块的功能
  • 需要分阶段交付的中大型功能
  • 修改超过 5 个文件或 ~200+ 行变更
  • 预计需要多个 AI 会话
  • 有未解决的产品或技术风险
Verification Baseline 验证基线

三层验证体系，确保变更不会悄悄破坏东西：

层级命令用途频率
快速检查typecheck + 单元测试秒级，修改后必跑每次代码变更
冒烟测试UI 关键路径检查~10s，UI 改动必跑UI 变更时
完整 E2E跨页面端到端测试分钟级，大改动必跑发布前

4. Context 强制上下文层

v2.0.0 新增 docs/context/ 目录，包含 4 个强制模板文件，确保 AI 在执行任何非平凡任务前先读取项目上下文。

project-context.md NEW

项目身份、活跃工作、验证命令的单一真相源。

字段说明
项目名称 / 类型 / 最后更新基本身份信息
活跃需求 / 活跃 Owner Doc当前正在做什么
构建 / 测试 / 启动命令验证命令必须真实可执行，占位则填"无"
活跃 Plan 状态进行中的执行计划追踪
可选层激活状态audits / testing / retrospectives / skills / analysis
Documentation Freshnessfresh / partially stale / stale / unknown
ai-autonomy-policy.md NEW

定义 AI 在不同区域的自主级别和受保护区域。详见下方 第 5 节。

codebase-map.md NEW

代码库地图，记录关键目录和文件的职责映射。帮助 AI 快速定位相关代码。

source-of-truth-and-precedence.md NEW

定义文档间的优先级关系。当多个文档信息冲突时，明确以哪个为准。

关键约束：这 4 个文件是整体，必须一起存在才能保证 AI 上下文完整。缺失任何一个都会导致 AI 做出错误决策。

5. AI 自主级别策略

v2.0.0 引入 5 级 AI 自主权限模型，通过 ai-autonomy-policy.md 配置：

级别名称行为典型场景
implement 执行 直接执行，不需要问 低风险本地修改、有明确 owner doc
plan-first 计划优先 先出计划，等确认再执行 中等复杂度、涉及多模块
ask-first 先问 执行前必须确认 高风险变更、受保护区域
blocked 阻止 不能执行，必须人工介入 支付、数据删除、权限变更
research-only 仅研究 只研究报告，不执行 探索阶段、不确定是否该做

受保护区域示例

区域风险类型自主级别
认证/权限/支付/数据删除高ask-first
数据库 Schema 变更高ask-first
公共 API 契约高ask-first
部署配置中ask-first

6. 文档新鲜度追踪

通过 project-context.md 中的 Documentation Freshness 字段追踪文档与代码的一致性：

状态含义AI 行为
fresh所有上下文文件反映当前代码状态正常执行
partially stale部分文件过时，但不影响当前任务继续执行，标记过时部分
stale上下文严重过时必须先更新才能继续
unknown从未确认过一致性提醒用户确认
设计哲学：文档过时是 AI 犯错的首要原因。与其假装文档永远正确，不如显式追踪其新鲜度，让 AI 知道什么时候该怀疑、什么时候该信任。

7. Plan & Closure 审计

v2.0.0 在执行计划流程中引入双审计机制：

Plan Audit（计划审计）

时机：开始实施前

  • 目标清晰，与需求文档一致
  • 拆分步骤具体可执行
  • 风险已识别并有应对方案
  • 依赖项已确认
  • 验收标准明确
Closure Audit（闭包审计）

时机：标记完成前

  • 所有步骤已完成
  • 验证命令已运行并通过
  • 受影响的 owner docs 已更新
  • 计划与实际执行无重大偏离

8. 交互式确认流程

v2.0.0 新增 Step 0.5，在执行前先向用户展示检测结果并确认：

📋 docs-pipeline 配置检测

📌 文档模式：模式 A（文档跟随项目）
📁 文档根路径：./docs
📂 项目根路径：./
🔍 docs/ 状态：全新
📎 文档引用路径：docs/

用户可以通过 AskUserQuestion 工具修改：

  • 切换模式 A/B
  • 修改文档根路径
  • 跳过 ARCHITECTURE.md 生成
  • 跳过 Pensieve 集成
不会跳过：除非用户明确说"直接执行"或"不要问我"，否则交互确认始终执行。这是防止误操作的安全阀。

12. Pensieve 集成

Pensieve 是一个文档版本控制系统，v2.0.0 将其集成到 docs-pipeline 中：

  • 分支 A：检测到 .pensieve/ 已存在 → 执行 doctor → sync-instructions → .gitignore 保护 → doctor 验证
  • 分支 B：.pensieve/ 不存在 → 询问用户是否安装 → 用户确认则安装并走完整流程
注意：.pensieve/state.md 是运行时状态，每次操作都会变，必须通过 .gitignore 排除。
