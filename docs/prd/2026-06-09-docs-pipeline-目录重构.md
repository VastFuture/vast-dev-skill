## 1. 产品定位与背景

### 产品定位
docs-pipeline 是一个文档系统模板，为 AI 辅助开发项目提供标准化的目录结构和工作流程。

### 产品背景
当前 docs-pipeline 模板存在以下问题：

| 问题 | 描述 |
|------|------|
| **命名冲突** | `docs/design/`（单数）和 `docs/designs/`（复数）并存，让人迷惑 |
| **职责重叠** | 两个目录都叫"design"相关，边界模糊 |
| **哲学冲突** | AGE 设计驱动 vs DDD 代码驱动，两套互斥的哲学在同一模板中 |
| **引用不一致** | `index.md` 只引用 `design/`，但 `CLAUDE.md`/`AGENTS.md` 同时引用两个目录 |
| **目录臃肿** | 原有 14 个目录，部分目录职责不清或重叠 |

### 演进历史

```
v1.0.0 ──▶ v2.0.0 ──▶ v4.4.0 ──▶ 重构
 │           │           │          │
 │           │           │          └─ 合并 DDD + AGE，精炼为 10 个目录
 │           │           │
 │           │           └─ 新增 designs/，引入代码驱动哲学
 │           │
 │           └─ 集成 AGE 工程规则，保留 design/
 │
 └─ 基础 docs pipeline，只有 design/
```

**关键提交**：
- `595517d`（2026-06-02）：v2.0.0 集成 AGE 工程规则
- `1af045f`（2026-06-05）：v4.4.0 新增 designs/ + standards/

## 4. 功能清单

### 4.1 目录结构（10 个目录）

| 目录 | 职责 | 更新频率 | 来源 |
|------|------|---------|------|
| `context/` | 项目上下文、真相优先级、验证命令 | 中频 | AGE |
| `backlog/` | 工作队列、待定事项、优先级排序 | 高频 | AGE |
| `prd/` | 需求规格、用户故事、验收标准 | 中频 | DDD |
| `design/` | 应用层设计 + 系统现状（SDD 驱动） | 中频 | AGE + DDD |
| `architecture/` | 技术基线、模块边界、分层规范 | 低频 | AGE |
| `standards/` | 开发规范、代码标准 | 低频 | DDD |
| `plans/` | 执行计划、任务拆解、变更记录 | 中频 | AGE + DDD |
| `lessons/` | 经验教训、复盘记录 | 低频 | AGE |
| `logs/` | 开发日志、每日记录 | 高频 | AGE |
| `issues/` | Bug 追踪、问题记录 | 高频 | 通用 |

### 4.2 模板文件

| 文件 | 用途 |
|------|------|
| `docs/index.md` | 文档路由中枢，任务路由表 |
| `docs/prd/PRD-DESIGN-EXPERT.md` | PRD Design Expert 角色定义 |
| `docs/prd/TEMPLATE.md` | PRD 模板（10 个模块） |
| `docs/plans/TEMPLATE.md` | 执行计划模板 |
| `docs/issues/TEMPLATE.md` | 问题追踪模板 |

## 5. 实现逻辑

### 5.1 设计哲学融合

```
┌─────────────────────────────────────────────────────────────┐
│                    融合后的设计哲学                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ┌─────────────────────┐    ┌─────────────────────┐        │
│  │      AGE 哲学       │    │      DDD 哲学       │        │
│  │                     │    │                     │        │
│  │  设计是吸引子        │    │  代码是真相          │        │
│  │  代码向设计收敛      │    │  文档跟上代码        │        │
│  └──────────┬──────────┘    └──────────┬──────────┘        │
│             │                           │                   │
│             └───────────┬───────────────┘                   │
│                         │                                   │
│                         ▼                                   │
│              ┌─────────────────────┐                       │
│              │     SDD 驱动        │                       │
│              │                     │                       │
│              │  设计即文档          │                       │
│              │  单一真相源          │                       │
│              │  design/ 统一存放    │                       │
│              └─────────────────────┘                       │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 SDD 核心循环

```
设计意图（design/）
    │
    ▼ ① 先写设计
实现代码（src/）
    │
    ▼ ② 再写代码
测试验证（tests/）
    │
    ▼ ③ 验证通过
同步设计（design/）
    │
    ▼ ④ 更新为实现现状
闭包审计（lessons/）
```

### 5.3 生命周期流程

```
context/ ─────────────────────────────────────────────────▶
    │                                                      │
    ▼                                                      │
backlog/ ──▶ prd/ ──▶ design/ ──▶ architecture/           │
    │           │         │              │                  │
    │           │         │              │                  │
    │           ▼         ▼              ▼                  │
    │       standards/ ────────────────┘                   │
    │           │                                          │
    │           ▼                                          │
    └───────▶ plans/ ──▶ 实现 ──▶ issues/ ──▶ lessons/ ──▶ logs/
                     │
                     ▼
                design/（更新为实现现状）
```

## 6. 非功能需求

| 类别 | 需求 |
|------|------|
| **可用性** | 目录命名直观，新人 5 分钟内理解每个目录的职责 |
| **可维护性** | 每个目录有独立价值，无重叠职责 |
| **兼容性** | 兼容 AGE 和 DDD 两种工作流 |
| **性能** | 文档路由表查询效率 O(1) |
| **可扩展性** | 支持按需添加子目录（如 plans/completed/） |

## 9. 验收标准

| 编号 | 验收标准 | 优先级 |
|------|---------|--------|
| AC-01 | 目录数量为 10 个，无重叠职责 | P0 |
| AC-02 | `design/` 统一存放设计意图和实现现状 | P0 |
| AC-03 | `plans/completed/` 子目录存在 | P1 |
| AC-04 | `docs/index.md` 包含完整的目录路由表 | P0 |
| AC-05 | `prd/TEMPLATE.md` 包含 PRD Design Expert 角色定义 | P1 |

## 10. 风险与限制

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 已有项目迁移成本 | 需要更新所有引用 | 提供迁移脚本或指南 |
| 用户习惯改变 | 需要适应新目录结构 | 保持核心概念不变（如 design/ 保留） |
| AGE 哲学弱化 | design/ 不再是纯"吸引子" | 通过 SDD 循环保持设计优先 |
