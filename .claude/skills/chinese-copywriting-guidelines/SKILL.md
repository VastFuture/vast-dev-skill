# Chinese Copywriting Guidelines

IRON LAW: 只报告真实存在的排版问题,不要制造不存在的问题。修复必须基于具体规则,不能凭感觉。

## Workflow

Copy this checklist and check off items as you complete them:

```
Chinese Copywriting Guidelines Progress:

- [ ] Step 1: 理解输入与确定范围 ⚠️ REQUIRED
  - [ ] 1.1 确认检查对象(文案片段/单文件/项目目录)
  - [ ] 1.2 确认操作模式(仅检查/检查+修复)
  - [ ] 1.3 加载排版规则
- [ ] Step 2: 执行检查
  - [ ] 2.1 扫描空格问题
  - [ ] 2.2 扫描标点符号问题
  - [ ] 2.3 扫描全角半角问题
  - [ ] 2.4 扫描专有名词问题
- [ ] Step 3: 生成报告 ⚠️ REQUIRED
  - [ ] 3.1 按优先级分类问题
  - [ ] 3.2 展示问题位置与修复建议
  - [ ] 3.3 如果需要修复,确认用户意图
```

## Step 1: 理解输入与确定范围 ⚠️ REQUIRED

### 1.1 确认检查对象

Ask yourself:
- 用户提供的是什么? (一段文本/文件路径/目录路径)
- 检查范围是什么? (单个文案/单个文件/整个项目)

### 1.2 确认操作模式

Ask user:
- 仅检查并报告问题?
- 检查并自动修复?
- 检查后让我选择性修复?

如果用户没有明确说明,默认为"检查并报告,等待用户确认后再修复"。

### 1.3 加载排版规则

→ Load references/spacing-rules.md (空格规则)
→ Load references/punctuation-rules.md (标点符号规则)
→ Load references/proper-nouns.md (专有名词规则)

## Step 2: 执行检查

### 2.1 扫描空格问题

Ask yourself these questions:

1. **中英文之间是否有空格?**
   - 正确: `在 LeanCloud 上`
   - 错误: `在LeanCloud上`, `在 LeanCloud上`

2. **中文与数字之间是否有空格?**
   - 正确: `今天出去买菜花了 5000 元`
   - 错误: `今天出去买菜花了 5000元`, `今天出去买菜花了5000元`

3. **数字与单位之间是否有空格?**
   - 正确: `我家的光纤入屋宽带有 10 Gbps`
   - 错误: `我家的光纤入屋宽带有 10Gbps`
   - 例外: 度数/百分比不加空格 `90°`, `15%`

4. **全角标点与其他字符之间是否有多余空格?**
   - 正确: `刚刚买了一部 iPhone,好开心!`
   - 错误: `刚刚买了一部 iPhone ,好开心!`

### 2.2 扫描标点符号问题

Ask yourself:
- 是否有重复使用的标点符号? (如 `!!!`, `??!!`)
- 中文内容是否使用了全角标点? (`,。!?`)
- 英文内容是否使用了半角标点? (`,. !?`)
- 数字是否使用了半角字符?

### 2.3 扫描全角半角问题

Ask yourself:
- 中文标点是否使用全角? (`,。!?「」`)
- 数字是否使用半角? (`1000` 而不是 `１０００`)
- 英文内容是否使用半角标点?

### 2.4 扫描专有名词问题

Ask yourself:
- 专有名词大小写是否正确? (`GitHub` 不是 `github` 或 `Github`)
- 产品名称是否按照官方格式书写?

Common mistakes:
- `github` → `GitHub`
- `Javascript` → `JavaScript`
- `Iphone` → `iPhone`
- `Macos` → `macOS`

## Step 3: 生成报告 ⚠️ REQUIRED

### 3.1 按优先级分类问题

| 级别 | 说明 | 示例 |
|------|------|------|
| P0 - 严重 | 影响阅读理解,专业形象严重受损 | 中英文完全没有空格,专有名词错误 |
| P1 - 高 | 明显不符合规范,影响专业度 | 数字与单位没空格,标点符号错误 |
| P2 - 中 | 不影响理解但不规范 | 个别位置缺少空格 |
| P3 - 低 | 争议性用法,可选修复 | 直角引号 vs 弯引号 |

### 3.2 展示问题位置与修复建议

For each issue, provide:
1. **位置**: 文件名和行号(如果适用)
2. **原文**: 有问题的文本片段
3. **问题**: 违反了哪条规则
4. **修复**: 修正后的文本
5. **优先级**: P0/P1/P2/P3

Output format:
```
## 排版问题报告

### P0 - 严重问题 (2处)
1. [第3行] 中英文之间缺少空格
   原文: `在GitHub上使用LLM`
   修复: `在 GitHub 上使用 LLM`

### P1 - 高优先级问题 (5处)
...

### 统计
- 总问题数: 12
- P0: 2, P1: 5, P2: 3, P3: 2
```

### 3.3 确认用户意图

Ask user:
- 全部修复?
- 只修复 P0/P1?
- 让我选择性修复?
- 仅查看报告,不修复?

⚠️ Do NOT proceed to Step 4 without user confirmation.

## Step 4: 执行修复 (conditional)

Only proceed if user confirms.

### 4.1 应用修复

根据用户选择应用修复:
- 如果是单个文案片段: 直接输出修复后的文本
- 如果是文件: 写入修复后的内容
- 如果是项目: 逐个文件修复

### 4.2 保存修复后的内容

For files:
- 默认覆盖原文件
- 如果用户要求保留原文件,创建 `{filename}-fixed.md`

### 4.3 展示修复摘要

Output:
```
## 修复完成

### 修复统计
- 修复文件数: 3
- 修复问题数: 12 (P0: 2, P1: 5, P2: 3, P3: 2)

### 修复的文件
1. README.md (4处)
2. docs/guide.md (6处)
3. docs/api.md (2处)
```

## Anti-Patterns

Do NOT:
- 把英文句号 `.` 改成中文句号 `。` 除非整句都是中文
- 在代码块、命令、URL中添加空格
- 在专有名词内部添加空格 (如 `GitHub` 不要变成 `Git Hub`)
- 报告不存在的问题 (比如原文本已经符合规范)
- 修改引用的英文原文中的标点符号
- 在 inline code (`` `code` ``) 和中文之间强制加空格(这是可选的)

## Common Edge Cases

### 例外情况1: 代码与文本混排
```markdown
使用`git commit -m "message"`提交代码

可以不在 inline code 和中文之间加空格,也可以加:
使用 `git commit -m "message"` 提交代码
```
两种都可以,不强制修复。

### 例外情况2: 度数与百分比
```markdown
正确: 90° 的角, 15% 的提升
错误: 90 ° 的角, 15 % 的提升
```

### 例外情况3: 产品名称特殊格式
按照官方格式书写,即使不符合一般规则:
- 豆瓣FM (不是 豆瓣 FM)
- 小米MIX (按官方格式)

### 例外情况4: 英文整句
当完整的英文句子出现时,其内部使用半角标点:
```markdown
正确: 乔布斯那句话是怎么说的?「Stay hungry, stay foolish.」
错误: 乔布斯那句话是怎么说的?「Stay hungry,stay foolish。」
```

## Pre-Delivery Checklist

### 检查阶段
- [ ] 所有扫描规则都已应用
- [ ] 问题按优先级正确分类
- [ ] 每个问题都有明确的位置、原文、修复建议
- [ ] 没有误报(原本正确的被标记为错误)

### 修复阶段(如果执行了修复)
- [ ] 修复操作已获得用户确认
- [ ] 只修复了用户确认的优先级问题
- [ ] 没有修改代码块、URL、命令中的内容
- [ ] 没有破坏原文的语义
- [ ] 修复后的文本符合所有排版规则

### 输出质量
- [ ] 报告清晰易读,问题定位准确
- [ ] 统计数据准确
- [ ] 如果是项目批量检查,有汇总报告
