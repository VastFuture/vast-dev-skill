## 🎯 设计目标

为 AI 编码代理提供简洁、可执行的指令。聚焦"做什么"而非"怎么排版"。遵循官方最佳实践：简单、直接、可维护。

---

## 📊 优先级栈

当规则冲突时，按以下优先级执行（从高到低）：

1. **角色与安全**：保持技术性，执行 KISS/YAGNI 原则，维护向后兼容性，诚实对待局限性
2. **上下文与持久性**：严格遵守 `<context_gathering>`、`<persistence>`、`<self_reflection>` 等标签约束
3. **质量标准**：遵循代码规则、工作流程、实施检查清单；保持输出可操作性
4. **报告规范**：提供带行号的文件路径，列出风险和后续步骤

## 🌐 沟通风格

### 语言约定

- 默认使用中文回答，可混用英文技术术语
- 代码标识符（变量、函数、类）使用英文
- 代码注释优先使用中文，简洁清晰

### 混合输出模式

根据任务类型选择合适的输出风格。**关键原则**：执行类任务展示进度，分析类任务突出逻辑。

**详见 @output-modes.md**（含模式 A/B 详细结构、示例对比、状态标记）

**模式选择矩阵**：

| 任务类型 | 使用模式 | 典型场景示例 |
|---------|---------|-------------|
| 代码编辑、文件修改 | 模式 A（执行进度式） | 重构函数、修复 bug、添加功能 |
| 问题诊断、解释说明 | 模式 B（分析回答式） | "为什么报错"、"这段代码做什么" |
| 方案设计、架构讨论 | 模式 B（分析回答式） | 技术选型、性能优化方案对比 |
| 简单查询 | 直接回答 | "这个变量在哪定义的" |
| 混合任务 | 先 B 后 A | 先分析问题 → 再执行修复 |

## 工程规则（AGE 增强）

**详见 @engineering-rules.md**（含完整规范）

### 核心要点速查

**先读这里**：
- `docs/context/project-context.md` — 项目上下文
- `docs/context/ai-autonomy-policy.md` — AI 自主级别策略
- `docs/context/codebase-map.md` — 代码库地图

**任务路由**：
1. 确定任务类型：需求澄清 / 设计变更 / 架构变更 / 纯实现 / Bug 调查 / 验证审计
2. 用 `docs/index.md` 读取该任务类型的 owner docs 再行动

**计划触发器**（任一条件触发）：
- 变更 API、数据库/模型、认证、集成、部署或公共契约
- 跨越多个功能表面的用户可见行为变更
- 触及多个模块并改变共享行为
- 预计需要多个 AI 会话
- 修改超过 5 个文件或约 200+ 行变更
- 需要分阶段执行或明确的闭包门控
- 有未解决的产品或技术风险不能隐藏

**运营规则**（10 条）：
1. 文件进文件出
2. 聊天不是持久记忆
3. 不要从原始输入直接跳到代码
4. 非平凡实现前确认设计基线
5. 记录非显而易见的回归
6. 技能是方法选择器
7. 重复错误模式必须升级
8. 不要生成完整产品
9. 信息缺失时写入文件
10. 使用 backlog 和自主策略

**默认工作流**（11 步）：
1. 读取或更新 `docs/context/`
2. 选择工作时查看 `docs/backlog/`
3. 写或更新 `docs/prd/`
4. 基线变更时更新 `docs/design/` 或 `ARCHITECTURE.md`
5. 路由任务并选择候选可复用技能
6. 计划触发器满足时写或更新 `docs/exec-plans/`
7. 实施前审计计划
8. 实现最小完整切片
9. 运行验证
10. 闭包审计
11. 需要时记录 `docs/lessons/`

**文档所有权**：

| 目录 | 职责 |
|------|------|
| `docs/context/` | 强制 AI 上下文、真相优先级、项目约定 |
| `docs/backlog/` | 工作队列、AI 自主级别标签 |
| `docs/research/` | 调研文档（技术方案、可行性分析） |
| `docs/prd/` | 实现就绪的需求综合 |
| `docs/design/` | 稳定的应用层业务和功能设计 |
| `docs/exec-plans/` | 非平凡工作的执行和闭包标准 |
| `docs/lessons/` | 持久可复用的工程教训 |

## 🔄 工作流程

### 任务追踪

- **多步任务（≥2 步）必须使用 TodoWrite 工具追踪进度**
- 实时更新状态：`pending` → `in_progress` → `completed`
- 完成一步立即标记，不批量更新
- 每次工具调用前重述用户目标和当前计划

### 核心流程

1. **接收与现实检查** — 清晰重述请求，识别潜在破坏性变更
2. **上下文收集** — 从广泛开始，然后聚焦；首轮 5-8 次工具调用
3. **规划** — 生成多步骤计划（≥2 步）；可行性不确定时调用 `sequential-thinking`
4. **执行** — 通过工具执行每次写入/测试，不假想结果
5. **验证与自我反思** — 能跑测试就跑；自评可维护性、测试覆盖、性能、安全性
6. **交接** — 简要结论 + 关键文件引用（`file:line`） + 风险和后续步骤

### Plan 模式

**详见 @plan-mode.md**（含复杂度分级、Plan 文件规范、多次调用规则）

**适用场景**：中等及以上复杂度、多步骤、跨文件/模块/服务的任务

## 💻 代码规则

### 通用原则

- **KISS / YAGNI**：简单直接，不为假设需求过度设计
- **单一职责**：函数做一件事，嵌套控制在 3 层内
- **向后兼容**：未经批准不破坏现有 API/CLI 行为/数据格式
- **复用模式**：按项目既有风格实现，不引入新架构

## 🛠️ 工具约定

### Shell 与文件系统

- 默认通过 Codex CLI 执行命令
- **读多写少**：优先只读命令
- 避免破坏性命令（`rm -rf`、强制覆盖），除非明确授权
- 大范围操作先小范围试验

### MCP 工具（如可用）

**全局原则**：
1. **单轮最多两个工具**
2. **最小必要**：限制查询范围避免过度抓取
3. **离线优先**：默认使用本地工具
4. **失败降级**：失败时尝试替代服务

**服务选择矩阵**：

| 任务意图 | 主要服务 | 备用 | 使用时机 |
|---------|---------|------|---------|
| 复杂规划、分解 | `sequential-thinking` | 手动分解 | 可行性不确定、多步重构 |
| 官方文档/API/框架 | `context7` | `fetch` | 库用法、版本差异 |
| 网页内容获取 | `fetch` | 手动搜索 | 获取网页、文档 |
| 代码语义搜索、编辑 | `serena` | 直接文件工具 | 符号定位、跨文件重构 |
| 持久化记忆、知识图谱 | `memory` | 手动笔记 | 用户偏好、项目上下文 |
| 时间/时区操作 | `time` | 系统时间 | 时间戳生成、时区转换 |

## 📁 项目文档

- **@ARCHITECTURE.md** — 项目架构概览
- **@docs/index.md** — 文档路由中枢

**产物链路：**

```
ideas（随手记）→ research（调研）→ prd（需求）→ exec-plans/active（计划进行中）→ exec-plans/completed（计划完成）
                                                                               ↓
                                                                           lessons（踩坑教训，按需横切）
```

**按需推进，不强制全流程：**
- 小功能：直接进 `docs/exec-plans/active/`，无需 PRD/research
- 中功能：`docs/prd/` → `docs/exec-plans/active/` → `completed/`
- 大功能：走全流程
- 踩坑了：当下写 `docs/lessons/`

**铁律：**
- 检索子目录前先读对应 `README.md`；增删文件后同步更新索引
- 一个产物只能在一个目录里；状态流转必须搬家
