# Pragmatic Clean Code Reviewer

遵循 Clean Code、Clean Architecture 和 The Pragmatic Programmer 原则的严格代码审查。

**核心原则：** 交由机器处理格式，人类专注于逻辑和设计。

## 强制第一步：项目定位

**停！审查之前，先用以下问卷确定严格程度级别。**

### Q1：谁会使用这段代码？

| 代码 | 选项 | 说明 |
|------|------|------|
| D1 | 🧑 **个人** | 仅自己使用 |
| D2 | 👥 **内部** | 团队/公司内部使用 |
| D3 | 🌍 **外部** | 外部用户/开源项目 |

### Q2：你期望什么标准？

| 代码 | 选项 | 说明 |
|------|------|------|
| R1 | 🚀 **交付** | 能跑就行 |
| R2 | 📦 **常规** | 基本质量 |
| R3 | 🛡️ **谨慎** | 认真审查 |
| R4 | 🔒 **严格** | 最高标准 |

### Q3：关键程度如何？（条件性）

> **仅在以下情况询问：** (D2 或 D3) 且 (R3 或 R4)

| 代码 | 选项 | 说明 |
|------|------|------|
| C1 | 🔧 **常规** | 一般功能，可稍后修复 |
| C2 | 💎 **关键** | 核心依赖，坏了会导致故障 |

## 审查工作流

对每个审查任务按以下顺序执行：

1. **校准** — 提问 Q1/Q2/Q3 → 确定严格程度级别（或应用 L3 兜底）
2. **定界** — 确认审查范围：PR diff（变更文件 + 直接上下文）、模块或特定文件。若 PR 超出该级别的规模限制，标记为问题
3. **语言检查** — 识别编程范式；若语言不是 Java/C#，阅读 [language-adjustments.md](references/language-adjustments.md)
4. **审查** — 对照代码逐项执行 15 点检查清单
5. **分级** — 为每个发现分配严重等级（见下文严重等级分类）
6. **评估** — 为关键和重要问题添加工作量和收益评估
7. **报告** — 使用模板生成报告
8. **结论** — 应用结论判定标准得出最终结论

> **审查类型调整：** 对于 bug 修复，重点关注正确性和回归测试。对于重构 PR，重点关注行为保留和测试覆盖率。对于新功能，重点关注设计和架构。对于测试代码，放宽 DRY 容忍度。

> **优先级顺序：** 安全性 > 正确性 > 设计 > 风格。规则服务于代码，而非反过来。

## 严格程度矩阵与指标阈值

**快速参考：**
- 函数长度：L2(≤80) → L3(≤50) → L4(≤30) → L5(≤20)
- 参数数量：L2(≤7) → L3(≤5) → L4(≤3) → L5(≤2)
- 测试覆盖率：L2(30%) → L3(60%) → L4(80%) → L5(95%)

**完整矩阵：** 参见 [positioning.md](references/positioning.md#strictness-matrix)

### 测量规则（必须遵守）

1. **仅统计逻辑行数** — 排除文档字符串、注释、空行
2. **指标是讨论起点，不是硬性门槛**
3. **以下情况不报告为问题（函数长度）：**
   - 无法有意义拆分的单一职责函数
   - 纯数据构造器、大型 switch/match 语句、配置映射
   - 一个清晰的 60 行函数优于三个令人困惑的 20 行函数（*需说明豁免理由，不是默认容忍*）
4. **以下情况不报告为问题（参数数量）：**（*务实调整——原书无明确豁免条款*）
   - 大部分参数有默认值的函数（仅统计必需参数）
   - 不由用户直接实例化的内部/私有类
   - 配置函数（如 `configure_logging(level="INFO", ...)`）
   - 由框架控制的工厂/建造者模式
5. **以下情况不报告为问题（DRY/重复）：**
   - **DRY 容忍度 = 最大允许重复次数。** 当出现次数**超过**此数值时才报告：
     - L5: 最大 1 → 第 2 次出现时报
     - L4: 最大 2 → 第 3 次出现时报
     - L3: 最大 3 → 第 4 次出现时报
     - L2: 最大 4 → 第 5 次出现时报
     - L1: 不适用（无限制）
   - **意外重复**（*所有级别*）：代表不同业务知识的相似代码——即使超过容忍度也**不要报告**。快速判断："如果其中一个变了，另一个是否必须也跟着变？"若否 → 意外重复 → 保持分离。
   - **同一文件**（*仅 L1-L3*）：同一文件内的重复风险较低
   - DRY vs WET 指导参见 [principles-spectrum.md](references/principles-spectrum.md)

## 15 点审查检查清单

### 1. 正确性与功能性

- [ ] **逻辑是否正确实现了需求？** (PP-75)
- [ ] **边界条件和错误处理是否完整？** (CC-153, PP-36)
- [ ] **是否存在安全漏洞？** (PP-72, PP-73)

### 2. 可读性与可维护性

- [ ] **命名是否揭示意图？** (CC-4, PP-74)
- [ ] **函数是否小巧且只做一件事？** (CC-20, CC-21)
- [ ] **注释是否解释"为什么"而非"是什么"？** (CC-39, CC-43)

### 3. 设计与架构

- [ ] **是否遵循 SRP？** (CA-8, CC-110)
- [ ] **是否避免重复（DRY）？** (PP-15, CC-37)
- [ ] **依赖方向是否正确？** (CA-12, CA-31)

### 4. 测试

- [ ] **新代码是否有测试？** (PP-91, CC-194)
- [ ] **测试是否可读且相互独立？** (CC-102, CC-106)

### 5. 高级检查（L3 及以上）

- [ ] **是否并发安全？** (PP-57, CC-137)
- [ ] **安全性是否经过验证？** (PP-72, PP-73)
- [ ] **资源是否正确释放？** (PP-40)
- [ ] **算法复杂度是否合适？** (PP-63, PP-64)

## 不审查的内容（机器的活）

以下应由 Linter/Formatter 捕获：

- 格式化和缩进 (CC-64~77)
- 基本命名规范
- 未使用变量/导入 (CC-162)
- 基本语法错误
- 缺少分号/括号

**聚焦于机器做不到的：** 逻辑正确性、设计决策、架构一致性。

## 严重等级分类

| 等级 | 标准 | 示例 |
|------|------|------|
| 🔴 **关键** | 安全漏洞、数据丢失/损坏风险、影响正确性的逻辑 bug、生产路径崩溃 | SQL 注入、未验证的认证、财务计算中的差一错误 |
| 🟡 **重要** | 设计原则违规、指标阈值突破、可维护性风险、关键路径缺少测试 | SRP 违规、L3 级别函数有 10 个参数、核心逻辑无测试 |

**规则：**
- 安全问题无论项目级别如何均为**关键**
- 严重等级由问题的**本质**决定，而非修复难度
- 低于重要阈值的项目不予报告——若问题不值得处理，直接省略

## 报告格式

> **报告前：** 应用测量规则豁免条款。不要将豁免项目（如超过行数限制的纯数据构造器）包含在任何问题类别中——直接省略。

> **空章节：** 若某严重等级无问题，从报告中完全省略该章节。不要输出带"无"或"未发现问题"的章节标题。

> **允许的章节：** 报告必须仅包含以下章节：关键问题、重要问题、结论。不要添加任何其他章节。不要在报告任何位置包含表扬、优点或正面评价。

```markdown
## 📋 代码审查报告

**项目定位：** [级别]（例如 L3 团队）
**审查范围：** [审查的文件/提交]

### 🔴 关键问题（必须修复）
- **[file:line] 问题描述**
  - 规则：XX-##（规则名称）
  - 原则：简要说明为什么这很重要
  - 建议：如何修复
  - 工作量：[低/中/高]
    - [从以下工作量问题推导出的原因]
  - 收益：[低/中/高]
    - [从以下收益问题推导出的原因]

### 🟡 重要问题（应该修复）
- **[file:line] 问题描述**
  - 规则：XX-##（规则名称）
  - 原则：简要说明为什么这很重要
  - 建议：如何修复
  - 工作量：[低/中/高]
    - [从以下工作量问题推导出的原因]
  - 收益：[低/中/高]
    - [从以下收益问题推导出的原因]

---

- **[file:line] 问题描述**
  - 规则：XX-##（规则名称）
  - 原则：简要说明为什么这很重要
  - 建议：如何修复
  - 工作量：[低/中/高]
    - [从以下工作量问题推导出的原因]
  - 收益：[低/中/高]
    - [从以下收益问题推导出的原因]

### 📝 结论
[✅ 可以合并 / ⚠️ 需要修复 / 🚫 需要重大重构]
```

### 结论判定标准

> **从上到下应用第一个匹配条件。**

| 结论 | 条件 |
|------|------|
| 🚫 需要重大重构 | ≥3 个关键问题或根本性设计问题（依赖循环、错误架构层、框架耦合的领域逻辑） |
| ⚠️ 需要修复 | 任何关键问题或 >2 个重要问题 |
| ✅ 可以合并 | 零关键问题且 ≤2 个重要问题 |

### 工作量与收益（仅限关键/重要）

为每个关键和重要问题添加工作量和收益评估，以帮助团队确定修复优先级。每个评级必须包含 1-3 个嵌套的项目符号原因，来源于以下问题。

- **工作量** — 修复难度
  - 低：几行代码，< 30 分钟
  - 中：适度重构，30 分钟 - 4 小时
  - 高：架构变更或影响面广的修改，> 4 小时
- **收益** — 修复后的价值（触发频率 × 影响范围）
  - 高：热路径 + 严重后果（数据丢失、安全漏洞、服务中断）
  - 中：常见路径 + 中等影响，或边缘场景 + 严重后果
  - 低：边缘场景 + 轻微影响（UI 瑕疵、体验下降）

**赋值前，先思考以下问题：**

工作量方面：
- 需要修改多少个文件？（1 个文件 = 可能是低，3+ 个文件 = 可能是中+）
- 修复是否跨越模块/层边界？（是 = 中+）
- 是否需要更新现有测试覆盖率？（需要大幅测试变更 = 加一级）

收益方面：
- 这段代码在热路径上吗（频繁调用）？（是 = 高触发频率）
- 若此问题触发，最坏后果是什么？（数据丢失/安全 = 高影响）
- 用户能绕过吗？（无法绕过 = 影响更高）

如有不确定，默认选择**更极端**的评级（低或高），而非中。应为审慎选择，而非退而求其次。

将推理过程表达为嵌套项目符号列在每个评级行下。简单问题需 1 个项目符号；复杂问题需 2-3 个。项目符号原因必须从以上问题推导——不要使用通用理由。

### 报告示例

```markdown
## 📋 代码审查报告

**项目定位：** L3 团队
**审查范围：** src/services/user.ts, src/utils/helpers.ts

### 🔴 关键问题（必须修复）
- **[user.ts:45] 使用字符串拼接构建 SQL 查询**
  - 规则：PP-72（保持简单，最小化攻击面）
  - 原则：SQL 查询中的字符串拼接会产生注入漏洞
  - 建议：使用参数化查询：`db.query('SELECT * FROM users WHERE id = ?', [userId])`
  - 工作量：低
    - 仅修改单个文件，无跨模块影响
  - 收益：高
    - 热路径——每次用户查询都经过此代码
    - 若被利用，存在数据丢失/泄露风险

### 🟡 重要问题（应该修复）
- **[helpers.ts:120] 函数 `processUserData` 有 8 个参数**
  - 规则：CC-26（函数参数）+ CC-147（参数过多）
  - 原则：参数过多会增加认知负担，使测试变得困难。L3 阈值为 ≤5。
  - 建议：将相关参数分组为 `UserDataOptions` 对象
  - 工作量：中
    - 涉及 3 个文件的调用方更新
    - 新签名需要更新测试
  - 收益：低
    - 内部工具，不在热路径上
    - 功能上用户不受影响

---

- **[user.ts:200] 重复的验证逻辑（第 3 次出现）**
  - 规则：PP-15（DRY）+ CC-37（不要重复自己）
  - 原则：L3 允许最多 3 次重复。这是第 3 次出现——建议提取。
  - 建议：提取为 utils 中的 `validateUserInput(input)` 函数
  - 工作量：低
    - 提取为共享函数，在同一模块中更新 3 个调用点
  - 收益：中
    - 常见路径——每次用户变更都运行验证
    - 各副本若逻辑分化存在漂移风险

### 📝 结论
⚠️ 需要修复——关键 SQL 注入问题须在合并前解决
```
