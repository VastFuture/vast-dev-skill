# Fireworks Tech Graph

生成生产级质量的 SVG 技术图表，并通过 `rsvg-convert` 导出为 PNG。

## 安装来源

从 GitHub 安装此技能：

```bash
npx skills add yizhiyanhua-ai/fireworks-tech-graph
```

公开包页面：

```text
https://www.npmjs.com/package/@yizhiyanhua-ai/fireworks-tech-graph
```

不要将 `@yizhiyanhua-ai/fireworks-tech-graph` 直接传给 `skills add`，因为 CLI 期望的是 GitHub 或本地仓库来源。

更新命令：

```bash
npx skills add yizhiyanhua-ai/fireworks-tech-graph --force -g -y
```

## 辅助脚本（推荐使用）

`scripts/` 目录下的四个辅助脚本提供稳定的 SVG 生成和验证：

### 1. `generate-diagram.sh` - 验证 SVG + 导出 PNG
```bash
./scripts/generate-diagram.sh -t architecture -s 1 -o ./output/arch.svg
```
- 验证已存在的 SVG 文件
- 验证通过后导出 PNG
- 示例：`./scripts/generate-diagram.sh -t architecture -s 1 -o ./output/arch.svg`

### 2. `generate-from-template.py` - 从模板创建起始 SVG
```bash
python3 ./scripts/generate-from-template.py architecture ./output/arch.svg '{"title":"My Diagram","nodes":[],"arrows":[]}'
```
- 加载内置 SVG 模板
- 从 JSON 输入渲染节点、箭头和图例项
- 转义文本内容以保持输出 XML 有效

### 3. `validate-svg.sh` - 验证 SVG 语法
```bash
./scripts/validate-svg.sh <svg-file>
```
- 检查 XML 语法
- 验证标签配对
- 验证 marker 引用
- 检查属性完整性
- 验证路径数据

### 4. `test-all-styles.sh` - 批量测试所有样式
```bash
./scripts/test-all-styles.sh
```
- 测试多种图表尺寸
- 验证所有生成的 SVG
- 生成测试报告

**何时使用脚本：**
- 生成复杂 SVG 时使用脚本以避免语法错误
- 脚本提供自动验证和错误报告
- 推荐用于生产图表

**何时直接生成 SVG：**
- 元素较少的简单图表
- 快速原型
- 需要完全控制 SVG 结构时

## 工作流（始终按此顺序执行）

1. **分类** 图表类型（见下方图表类型）
2. **提取结构** — 从用户描述中识别层、节点、边、流和语义分组
3. **规划布局** — 应用该图表类型的布局规则
4. **加载样式参考** — 始终加载 `references/style-1-flat-icon.md`，除非用户指定其他；加载对应的 `references/style-N.md` 以获取精确的颜色标记和 SVG 模式
5. **映射节点到形状** — 使用下方形状词汇表
6. **检查图标需求** — 加载 `references/icons.md` 了解已知产品
7. **编写 SVG** 并采用自适应策略（见 SVG 生成策略）
8. **验证**：运行 `rsvg-convert file.svg -o /dev/null 2>&1` 检查语法
9. **导出 PNG**：`rsvg-convert -w 1920 file.svg -o file.png`
10. **报告** 生成的文件路径

## 图表类型及布局规则

### 架构图
节点 = 服务/组件。按**水平层**分组（从上到下或从左到右）。
- 典型层：客户端 → 网关/负载均衡 → 服务层 → 数据/存储
- 使用 `<rect>` 虚线容器将同层的相关服务分组
- 箭头方向跟随数据/请求流
- ViewBox：`0 0 960 600` 标准，`0 0 960 800` 适用于高栈

### 数据流图
强调**数据移动到哪里**。聚焦数据转换。
- 为每条箭头标注数据类型（如 "embeddings"、"query"、"context"）
- 主数据路径使用更粗的箭头（`stroke-width: 2.5`）
- 虚线箭头表示控制/触发流
- 按数据类别着色箭头（不仅限 Agent/RAG — 使用语义）

### 流程图/过程流
顺序决策/处理步骤。
- 优先从上到下；宽流程可从左到右
- 菱形表示决策，圆角矩形表示过程，平行四边形表示输入/输出
- 保持节点标签简短（≤3 个词）；细节放在子标签中
- 节点对齐到网格：x 位置对齐到 120px 间隔，y 对齐到 80px

### Agent 架构图
展示 AI agent 如何推理、使用工具和管理内存。
始终要考虑的关键概念层：
- **输入层**：用户、查询、触发器
- **Agent 核心**：LLM、推理循环、规划器
- **记忆层**：短期（上下文窗口）、长期（向量/图数据库）、情景记忆
- **工具层**：工具调用、API、搜索、代码执行
- **输出层**：响应、行动、副作用
使用循环箭头（回路弧）展示迭代推理。视觉上分离不同记忆类型。

### 记忆架构图（Mem0、MemGPT 风格）
专注于记忆操作的专用 agent 图表。
- 分别展示记忆**写入路径**和**读取路径**（不同箭头颜色）
- 记忆层级：工作记忆 → 短期记忆 → 长期记忆 → 外部存储
- 标注记忆操作：`store()`、`retrieve()`、`forget()`、`consolidate()`
- 使用堆叠矩形或分层圆柱体表示存储层级

### 时序图
参与者之间的时间顺序消息交换。
- 参与者作为垂直**生命线**（顶部标签 + 垂直虚线）
- 消息作为生命线之间的水平箭头，时间从上到下
- 激活框（生命线上的薄填充矩形）显示活跃处理
- 使用 `<rect>` 循环/alt 框架分组，左上角有标签
- ViewBox 高度 = 80 + (消息数 × 50)

### 对比/特性矩阵
方法、系统或组件的并排对比。
- 列头 = 系统，行头 = 属性
- 行高：40px；列宽：最小 120px；表头行高：50px
- 已勾选单元格：淡背景色（如 `#dcfce7`）+ `✓` 勾选；不支持：`#f9fafb` 填充
- 交替行填充（`#f9fafb` / `#ffffff`）以提高可读性
- 最大可读列数：5；超过则拆分为两个图表

### 时间线/甘特图
水平时间轴显示持续时间、阶段和里程碑。
- X 轴 = 时间（周/月/季度）；Y 轴 = 项目/任务/阶段
- 条形：圆角矩形，按类别着色，内部或旁边标注
- 里程碑标记：特定 x 位置的菱形或实心圆，上方有标签
- ViewBox：`0 0 960 400` 典型；多时间段时 `0 0 1200 400`

### 思维导图/概念图
从中心概念放射状布局。
- 中心节点 `cx=480, cy=280`
- 第一层分支：均匀分布在中心周围（360/N 度）
- 第二层分支：以 30-45° 偏移从第一层分出
- 使用曲线 `<path>` 的三次贝塞尔曲线作为分支，不用直线

### 类图（UML）
展示类、属性、方法和关系的静态结构。
- **类框**：3 区间矩形（名称 / 属性 / 方法），最小宽度 160px
  - 顶部区间：类名，加粗，居中（抽象 = *斜体*）
  - 中部：带可见性的属性（`+` public，`-` private，`#` protected）
  - 底部：方法签名，相同可见性标记
- **关系**：
  - 继承（extends）：实线 + 空心三角形箭头，子 → 父
  - 实现（接口）：虚线 + 空心三角形，类 → 接口
  - 关联：实线 + 空心箭头，标签带多重性（1, 0..*, 1..*）
  - 聚合：实线 + 容器侧空心菱形
  - 组合：实线 + 容器侧实心菱形
  - 依赖：虚线 + 空心箭头
- **接口**：`<<interface>>` 刻板印象在名称上方，或圆形/棒棒糖表示法
- **枚举**：带 `<<enumeration>>` 刻板印象的区间矩形，底部为值
- 布局：父类在上，子类在下；接口在实现者左侧/右侧
- ViewBox：`0 0 960 600` 标准；深层层级 `0 0 960 800`

### 用例图（UML）
从用户视角看系统功能。
- **参与者**：火柴人（圆头 + 身体线）放在系统边界外
  - 标签在图形下方，13-14px
  - 主要参与者在左侧，次要/支持者在右侧
- **用例**：椭圆，内部居中标签，最小 140×60px
  - 名称用动词短语："Create Order"、"Process Payment"
- **系统边界**：大矩形，虚线边框，左上角系统名
- **关系**：
  - Include：虚线箭头 `<<include>>` 从基础用例指向被包含用例
  - Extend：虚线箭头 `<<extend>>` 从扩展用例指向基础用例
  - 泛化：实线 + 空心三角形（专用 → 通用）
- 布局：系统边界居中，参与者在外，用例在内
- ViewBox：`0 0 960 600` 标准

### 状态机图（UML）
实体的生命周期状态和转换。
- **状态**：圆角矩形，状态名，最小 120×50px
  - 内部活动：小文本 `entry/ action`、`exit/ action`、`do/ activity`
  - **初始状态**：实心黑圆（r=8），一条外出箭头
  - **最终状态**：实心圆（r=8）在空心圆（r=12）内
  - **判断**：小空心菱形，箭头上的守卫标签 `[condition]`
- **转换**：带可选标签的箭头 `event [guard] / action`
  - 守卫条件用方括号
  - 斜杠后为动作
- **组合/嵌套状态**：包含子状态的大矩形，带名称标签
- **分叉/汇合**：粗水平或垂直黑条（同步）
- 布局：初始状态左上，最终状态右下，流程从上到下
- ViewBox：`0 0 960 600` 标准

### ER 图（实体-关系）
数据库模式和数据关系。
- **实体**：矩形，标题加粗实体名，下方为属性
  - 主键属性：下划线
  - 外键：斜体或标记 (FK)
  - 最小宽度：160px；属性字体：12px
- **关系**：连接线上的菱形
  - 菱形内标签："has"、"belongs to"、"enrolls in"
  - 实体附近基数标签：`1`、`N`、`0..1`、`0..*`、`1..*`
- **弱实体**：双边框矩形 + 双菱形关系
- **关联实体**：菱形 + 矩形混合（内部有菱形的矩形）
- 线型：识别关系用实线，非识别关系用虚线
- 布局：实体排 2-3 行，相关实体之间有关系
- ViewBox：`0 0 960 600` 标准；多实体时 `0 0 1200 600`

### 网络拓扑
物理或逻辑网络基础设施。
- **设备**：图标样式的矩形或圆角矩形
  - 路由器：带交叉箭头的圆
  - 交换机：带箭头网格的矩形
  - 服务器：堆叠矩形（机架图标）
  - 防火墙：砖块图案矩形或盾牌形状
  - 负载均衡器：带箭头的水平分割矩形
  - 云：云形路径（重叠弧）
- **连接**：设备中心之间的连线
  - 以太网/有线：实线，带带宽标签
  - 无线：带 WiFi 符号的虚线
  - VPN：带锁图标的虚线
- **子网/区域**：带区域标签的虚线矩形容器（DMZ、Internal、External）
- **标签**：设备主机名 + 下方 IP，12-13px
- 布局：从上到下分层（Internet → Edge → Core → Access → Endpoints）
- ViewBox：`0 0 960 600` 标准

## 布局规则与验证

**间距**：
- 同层节点：水平 80px，垂直 120px（层之间）
- 画布边距：最小 40px，节点边缘之间 60px
- 对齐 8px 网格：水平 120px 间隔，垂直 120px 间隔

**箭头标签**（关键）：
- 必须有背景矩形：`<rect fill="canvas_bg" opacity="0.95"/>`，水平 4px、垂直 2px 内边距
- 放在箭头中部，≤3 个词，多条箭头汇聚时交错 15-20px
- 与节点保持 10px 安全距离

**箭头路由**：
- 优先使用正交（L 形）路径以减少交叉
- 箭头锚定在组件边缘，而非几何中心
- 绕过密集节点簇，并行箭头使用不同 y 偏移
- 不可避免的交叉使用跨弧（半径 5px）

**线条交叉预防**（关键 - Codex 上最常见的 bug）
当两条箭头必须交叉时，始终使用跨弧防止视觉重叠：
- 交叉的水平箭头：添加小半圆弧（半径 5px，与箭头同色，fill none）"跳过"另一条线
- SVG 跨弧模式：在下层使用白色/匹配背景弧，然后在上层绘制上层弧
- 多重交叉：交错弧半径（5px、7px、9px）以避免弧相互重叠
- 永远不要让两条箭头的直线段交叉而没有跨弧

**验证清单**（最终确定前运行）：
1. **箭头-组件碰撞**：箭头不得穿过组件内部（用正交路径绕行）
2. **文本溢出**：所有文本必须在 8px 内边距下适合（估算：`text.length × 7px ≤ shape_width - 16px`）
3. **箭头-文本对齐**：箭头端点必须连接到形状边缘（不能悬空）；所有箭头标签必须有背景矩形
4. **容器边界**：优先让箭头通过组件之间的开放间隙进出区域容器，而非穿过内部组件体

## SVG 技术规则

- ViewBox：`0 0 960 600` 默认；`0 0 960 800` 高；`0 0 1200 600` 宽
- 字体：通过 `<style>font-family: ...</style>` 内嵌 — 不要外部 `@import`（rsvg-convert 会中断）
- `<defs>`：箭头标记、渐变、滤镜、裁剪路径
- 文本：最小 12px，推荐 13-14px 标签，11px 子标签，16-18px 标题
- 所有箭头：`<marker>` 带 `markerEnd`，大小 `markerWidth="10" markerHeight="7"`
- 阴影：`<feDropShadow>` 在 `<filter>` 中，慎用（仅用于关键节点）
- 曲线路径：循环/反馈箭头使用 `M x1,y1 C cx1,cy1 cx2,cy2 x2,y2` 三次贝塞尔
- 裁剪内容：文本可能溢出节点框时使用 `<clipPath>`

## SVG 生成与错误预防

**强制：Python 列表方法**（始终使用）：
```python
python3 << 'EOF'
lines = []
lines.append('<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 960 700">')
lines.append('  <defs>')
# ... 每行单独处理
lines.append('</svg>')

with open('/path/to/output.svg', 'w') as f:
    f.write('\n'.join(lines))
print("SVG generated successfully")
EOF
```

**强制原因**：防止字符截断、打字错误和语法错误。每行独立，易于验证。

**工具调用前检查清单**（关键 - 每次都使用）：
1. ✅ 我现在能写出完整的命令/内容吗？
2. ✅ 我准备好所有必需的参数了吗？
3. ✅ 我检查过准备内容的语法错误了吗？

**如果任何答案为否**：停止。不要调用工具。先准备内容。

**错误恢复协议**：
- **第一次错误**：分析根本原因，应用针对性修复
- **第二次错误**：完全切换方法（Python 列表 → 分块生成）
- **第三次错误**：停止并报告给用户 — 不要无限循环
- **永远不要**：重试相同失败命令或用空参数调用工具

**验证**（生成后运行）：
```bash
rsvg-convert file.svg -o /tmp/test.png 2>&1 && echo "✓ Valid" && rm /tmp/test.png
```

**如果使用 `generate-from-template.py`**：
- 优先使用箭头 JSON 中的 `source`/`target` 节点 ID，以便生成器对齐到节点边缘
- 将 `x1,y1,x2,y2` 作为提示或后备坐标，不是主要路由原语
- 让生成器选择正交路由；除非路径保证清晰，否则避免硬编码中心到中心的直线

**常见语法错误避免**：
- ❌ `yt-anchor` → ✅ `y="60" text-anchor="middle"`
- ❌ `x="390`（缺少 y）→ ✅ `x="390" y="250"`
- ❌ `fill=#fff` → ✅ `fill="#ffffff"`
- ❌ `marker-end=` → ✅ `marker-end="url(#arrow)"`
- ❌ `L 29450` → ✅ `L 290,220`
- ❌ 末尾缺少 `</svg>`

## 样式选择

这些模式经常出现 — 将其内化：

**RAG 管道**：Query → Embed → VectorSearch → Retrieve → Augment → LLM → Response
**Agentic RAG**：在 Query 和 LLM 之间添加带工具使用的 Agent 循环
**Agentic Search**：Query → Planner → [Search Tool / Calculator / Code] → Synthesizer → Response
**Mem0 / 记忆层**：Input → Memory Manager → [Write: VectorDB + GraphDB] / [Read: Retrieve+Rank] → Context
**Agent 记忆类型**：感官（原始输入）→ 工作（上下文窗口）→ 情景（过去交互）→ 语义（事实）→ 程序性（技能）
**多 Agent**：编排器 → [子 Agent A / 子 Agent B / 子 Agent C] → 聚合器 → 输出
**工具调用流**：LLM → Tool Selector → Tool Execution → Result Parser → LLM（循环）
